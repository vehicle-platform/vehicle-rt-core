# src/services

Shared services the feature modules talk through. Features never include each other or `hal/`, only services (CI checks the `hal/` part). `can_if.h` exposes only the CAN types (`hal/can_types.h`), not the port functions. The same code runs on the host and on the H7 (D-034).

| Service | Status | What |
|---|---|---|
| `timebase` | done | `timebase_now_ms()` over `hal_time.h`, plus wrap-safe `timebase_elapsed_ms()` / `timebase_expired()` |
| `can_if` | done | The one reader of the CAN ports and the one TX path of features (≈ AUTOSAR CanIf as a concept, D-006). Receivers register per (port, ID, format), up to `CAN_IF_MAX_RECEIVERS` = 12 in a static table. `can_if_dispatch(port, max)` drains a port and calls them; frames with no receiver are counted. **Vehicle-bus guard (D-020, safety rule 2):** fixed and fail-closed. `CAN_PORT_VEHICLE` accepts only 29-bit `VEHICLE_CL250_REQUEST_ID` frames with DLC `VEHICLE_CL250_FRAME_DLC` that pass `vehicle_cl250_frame_allowed()`. Everything else gets `CAN_PORT_ERR_REFUSED` and is counted. **Port state (Ç1):** a bus-off or latched port (`services/can_sm`) takes no frame: `can_if_write()` returns `CAN_PORT_ERR_IO`, counted in `can_if_tx_blocked_count()`, never in the guard's refused counter, and `can_if_tx_free()` is false. `can_if_tx_allowed()` stays a pure check: the D-020 guard on the vehicle port; on the platform port it refuses a standard ID in an E2E-mandatory range (gen/ `PLATFORM_E2E_RANGE_*`: safety 0x010-0x07F, heartbeat 0x080-0x08F) unless that ID has a registered dedicated TX buffer (ISSUES E-14 (5)), counted in `can_if_tx_refused_count()`. `can_if_tx_abort_count()` tells the ISO-TP links about an N_As or bus-off abort. **Filters:** `can_if_apply_filters(port)` sets the port's acceptance filters to its registered receivers (platform UDS IDs to FIFO1) and seals the port: a later `can_if_register_rx()` there gets `CAN_IF_ERR_SEALED`. **Dedicated TX buffers (D-056):** `can_if_register_tx_dedicated(CAN_PORT_PLATFORM, id, ext)` (boot only, up to `CAN_IF_MAX_TX_DEDICATED` = 8; refused on the vehicle port, whose single TX buffer is fixed) gives a safety-range or heartbeat ID its own replace-on-new buffer; `can_if_apply_filters()` hands the list to the port first (`can_port_set_tx_dedicated()`) and seals only when both were accepted. `can_if_write()` is unchanged (guard, then port state, then the port routes by ID): for a dedicated ID it returns `CAN_PORT_TX_FULL` while the previous frame is still unsent (cancelled; write again in a later pass) and does not depend on `can_if_tx_free()`, which describes the Tx FIFO. A replace is never an N_As abort. |
| `can_sm` | done (Ç1) | CAN state manager per port (≈ AUTOSAR CanSM as a concept, D-006): pure core `can_sm_core` (ISO 11898-1 error active / passive / bus-off, plus a latch) and the glue that reads `hal/can_port.h` and carries out its actions. A bus-off aborts the pending TX and is counted; recovery waits a backoff that doubles after every attempt (1 s up to 30 s) and is back at 1 s after 30 s on the bus. The vehicle port uses the gen/ `VEHICLE_CL250_BUS_OFF_BACKOFF_*` and latches on its 5th bus-off since boot (D-030, D-054): no recovery until reboot. The platform port uses the same schedule as local provisional values and never latches (D-054). N_As: pending frames with no TX confirmation for `CAN_SM_TX_TIMEOUT_MS` (1000 ms, ISO 15765-2) are aborted. Every abort changes `can_sm_abort_seq()`. `can_sm_state_known(port)` is false before init, before the first controller snapshot and while the controller cannot be read (a latch stays known): the 0xFD02 health DID then reads UNKNOWN, never the last state (D-055). `can_sm_step(port)` runs before `can_if_dispatch(port)` (`app/comms`). Main loop only. |
| `vehicle_signals` | done | The last sample of every CL250 DID (raw, physical, and the send time of its DID's oldest unanswered read, D-051, so the age includes the round trip), written only by the UDS client (`features/uds`). Readers such as the platform-bus republisher (`features/vehicle_republish`) call `vehicle_signals_get(idx, now, &s)`. The state VALID / STALE / NONE is derived at read time from the generated `stale_after_ms` (D-025, D-029), so nothing stored can keep a value VALID. STALE is sticky until the next write (`vehicle_signals_expire()` every client step), so the ms counter wrap cannot revive a value. It also holds ECU presence. Static table, main loop only. |
| `diag` | done | rt-core's own DTC memory, the vehicle-tester status and the client's step counters for 0xFD02 (≈ AUTOSAR Dem as a concept, D-040, D-055). Writers of DTC results: the UDS client and server glue and `services/mailbox` (the two diagnostic-only `SAFETY_MAILBOX_*` DTCs, which set their status bytes but never the heartbeat's DEGRADED or ERROR_COUNT, D-093 amendment 3 addendum). DTCs are the gen/ table (`platform_uds.h`). Monitors report every pass (level-triggered): failed sets testFailed + confirmedDTC, passed clears testFailed. Only availability-mask bits are set. `diag_dtc_clear_all()` (UDS 0x14) zeroes the records, and an active condition sets them again on the next report. It never changes the condition itself (e.g. the UDS client latch). RAM only until the H7 flash driver. The step counters carry their write time: none since init or older than `PLATFORM_UDS_RT_CORE_HEALTH_MAX_AGE_MS` reads as not fresh (sticky, wrap-safe). Writers: the UDS client glue (status, step counters, its DTCs) and the UDS server glue (U3000-00 supervision, U0001-88 from `can_sm`). Readers: the UDS server glue and the heartbeat (`diag_fault_active()`, `diag_fault_onsets()`, D-064): every monitor's last result and the passed → failed onset count are kept apart from the status bytes, so a 0x14 clear neither hides an active fault nor re-counts it. `diag` includes no other service. Main loop only. |
| `com` + `com_core` | done (D-056 item 7) | The send path shared by rt-core's cyclic platform senders (≈ AUTOSAR Com as a concept, D-006), extracted from `features/vehicle_republish` when the heartbeat became the second sender. Pure `com_core`: the deadline-anchored cycle (`com_cycle_due()` / `com_cycle_done()`: due at once, then on the grid; missed deadlines skipped, never a burst; wrap-safe). `com_send()`: one frame to `CAN_PORT_PLATFORM` only through `can_if_write()`, then OK → `sent` (cycle done), `CAN_PORT_TX_FULL` → `retried` (try again next pass), anything else or a frame the sender could not build → `dropped` (cycle done). The sender owns its E2E state and commits it only on `CAN_PORT_OK` (D-056 item 5). Pack/unpack and E2E stay in gen/. Main loop only. |
| `snapshot` | done (D-065 PR 1) | Single-producer / single-consumer triple buffer between tasks of different priority (D-065 item 2: comms → EKF speed, EKF → comms lean, in PR 3). Generic and index-only: the caller owns `T slots[SNAPSHOT_SLOTS]`, the service hands out indices. The producer fills `slots[snapshot_write_index()]` and calls `snapshot_publish()` (one atomic exchange); the consumer calls `snapshot_read_index()` (one load, plus one exchange when something new was published) and always gets a valid slot: the newest complete record, or its previous one with `false`. Never a lock, a wait or a retry on either side, so never a seqlock (a higher-priority reader retrying while it preempts the writer would livelock, E-17 BLOCKER-2). Unread records are replaced, not queued. Defensive (safety-reviewer MINOR-3): an index outside the three slots read from the shared word is never used; that side latches its fault (`snapshot_producer_fault()` / `snapshot_consumer_fault()`, owning task only) and stops exchanging, so the consumer's record ages out by its stamp. Verified by unit tests, every interleaving of up to six operations at both preemption points on a hooked atomic double (`test_snapshot_interleave`), and a two-thread stress test under ASan and ThreadSanitizer. Initialise the snapshot and all three slots to a safe value (an explicit INVALID state, never a zero stamp) before either task starts. One producer and one consumer task per snapshot. |
| `alive` + `alive_core` | done (D-065 PR 1) | Alive supervision without a shared lock (D-064 item 4). `alive_counter_t` (one atomic word): the supervised task calls `alive_bump()` after each complete cycle (single writer), any task reads `alive_count()`. Pure `alive_core`: the supervisor's `alive_monitor_t` takes the count at registration as its baseline; a change is alive (stamped when seen), no change for more than the window is stalled (sticky until the next change, wrap-safe), and a count that never changed since registration is stalled at once (registered but never ran: no grace time). The zero state of a monitor is stalled (safety-reviewer MAJOR-1). Max-gap only (MINOR-5, accepted): one change ends a stall, so a task at a third of its rate still reads alive; 0x020's output-age budget (D-065 PR 3) covers that for the EKF. `app/comms` owns the EKF's monitor (`comms_ekf_t`, window `COMMS_EKF_ALIVE_WINDOW_MS` = gen/ `PLATFORM_EKF_LEAN_E2E_TIMEOUT_MS`) and hands the verdict to the heartbeat. |
| `imu` + `imu_core` | done (D-065 PR 3a) | The EKF's IMU input (D-065 item 2). **EKF task only.** `imu_read(imu, now, standstill)` drains the `hal/imu.h` FIFO once per EKF period (at most `IMU_DRAIN_MAX` = 64 pops; more is a BACKLOG and is flushed, as after a port fault) and returns one `imu_sample_t`: the x/y/z gyro rates as the **mean of every sample in (previous stamp, stamp]**, never a point sample (aliasing, safety-reviewer MAJOR-4 on PR 2), stamped at the read. INVALID, with rates 0 and the first failing reason: a port fault, a bad config (scale not finite/positive, ODR outside 800-1600 Hz, or a mean that is not finite), an overrun, a backlog, the first period, too few samples (below half of elapsed × ODR, or none: STALE), a sample at full scale (SATURATED), and no learnt z offset. Static state, no heap: `imu_t` is 60 B (M7), the drain uses one 6 B sample and a 20 B accumulator on the stack; M7 text 916 B (`imu_core`) + 192 B (`imu`). |

`snapshot`, `alive`, `derived_inputs` and `ride_records` (on a snapshot) are the only services shared between tasks. A snapshot has **one consumer call site**: a second `snapshot_read_index()` takes the newest record away from the first, and no slot index may be kept across another read (rule in `snapshot.h`). Anything else that needs the record gets a copy made by that one read site, as `services/lean_health` does for DID 0xFD03. They include `hal/hal_atomic.h`, so their headers bring it in transitively, like `can_if.h` brings `hal/can_types.h`; features call only the service functions, never `hal_atomic_*` (CI: `hal/hal_atomic.h` is included from `services/` and `hal/` only). `imu` belongs to the EKF task alone (CI: `hal/imu.h` is included from `services/imu.c` and `hal/` only). Every other service is main-loop (comms task) only; `timebase` is task-safe (`hal/hal_time.h`).

`can_if` runs in the main loop only and is not ISR-safe. On the H7, the FDCAN ISR will only queue frames, and `can_if_dispatch()` will drain that queue.

## Mailbox (D-093, M7 side)

The M4 safety partition's only data path (D-072 item 4c). Layout, slot order, HSEM IDs, region address and layout ID come only from gen/ `platform_mailbox.h` (defs v0.23.0): M7 -> M4 0x020 `EkfLean`, 0x022 `EkfFrictionMass`, 0x081 `HeartbeatRtCore` (class safety) and 0x120 `SafetyRequest` (class QM); M4 -> M7 0x023 `SafetyWarningStatus` and 0x082 `HeartbeatSafety`.

- **Region:** SRAM4 at `PLATFORM_MAILBOX_REGION_ADDR` (0x3800_0000), **`verified: false`** in defs (`PLATFORM_MAILBOX_ADDR_VERIFIED` = 0) until the CubeMX pin plan (roadmap S2) and the board confirm it with the SRAM4 ECC behaviour. This module never names the address: `mailbox_init(region, now)` takes the region from the H7 setup, which places it with the linker section and MPU region of D-093 item 3 and refuses a release image while the address is unverified. `mailbox.c` refuses to build when `VEHICLE_RTCORE_BIKE_IMAGE` is defined while the address is unverified. That setup is red-zone image code and does not exist yet, so **on the target the mailbox is inert** (`mailbox_step()` only counts skipped passes) until it does.
- **Access:** `mailbox_region_t` overlays the generated `platform_mailbox_t` with its 32-bit words (MISRA DEV-004); rt-core reads and writes only whole words through a volatile pointer, never memcpy or a byte store (SRAM4 ECC). Little-endian is checked at build time.
- **Ownership (gen/ `DIRECTION`):** the M7 writes its layout word every pass (a wiped word recovers in one pass) and the M7 -> M4 slots; it only reads the M4 layout word and the M4 -> M7 slots. `mailbox_init()` frees this core's mailbox HSEMs one by one and writes the M7 layout word; it never clears or initialises the region.
- **Writer:** `com_send()` offers a frame to its slot only after `CAN_PORT_OK`, i.e. exactly the frames whose E2E counter the sender commits (D-056 item 5), so the M4 sees the same counter sequence as the bus. `mailbox_step()` (comms pass, after 0x081 and 0x020) writes each pending frame: take the slot's HSEM (one step, interrupts masked), store payload and len words, DMB, `write_seq` + 1 (read-modify-write on the region), release. A refused HSEM defers the frame to the next pass (1 ms later): no wait, no retry loop. **Age limit (D-093 amendment 4, E-28 follow-up):** a deferred frame is never held longer than its message's cycle. The first pass that sees a pending frame stamps it with the `mailbox_step()` time (`com_send()` offers it earlier in the same comms pass, so the stamp is the offer time to within one pass; a newer offer replaces the frame and restamps); at each write attempt `mailbox_age_exceeds()` (pure, in `mailbox_core`, wrap-safe uint32 ms) drops the frame when it is **strictly** older than the cycle (age equal to the cycle is still written), counted in `write_aged` and `write_dropped`, before the HSEM is tried. The cycle is the gen/ `PLATFORM_<MSG>_CYCLE_TIME_MS` of the slot message (`platform.h`, `cycle_ms` in the slot table), never a literal. Without it, a deferred frame with nothing newer behind it (FDCAN2 bus-off while the M4 holds the HSEM) would reach the M4 late with a counter step of 1 and read as OK with a stale payload, bounded only by the E2E timeout; now the M4 reads the gap as WRONG_SEQUENCE (or INITIAL after its timeout). M4 -> M7 forwarding and the reader are unchanged. **Only into a matching peer (E-28 (5), user 2026-11-04):** while the M4 layout word differs from `PLATFORM_MAILBOX_LAYOUT_ID` (checked once per pass, after the M7 word is rewritten), no M7 -> M4 slot is written (an M4 built from other defs may own those words) and each pending frame is dropped (`write_dropped`), never deferred: a frame held through a mismatch shorter than its E2E timeout while `com_send()` offers nothing new (FDCAN2 bus-off, E-28 (1)) would reach the M4 late with a counter step of 1 and read as OK with a stale payload. After the match returns, the next committed frame (≤ one cycle) is written; the M4 reads the gap as WRONG_SEQUENCE, or INITIAL after its timeout, either not valid, and the D-101 item 4 return follows. This needs E2E max delta 1 on every slot message (`_Static_assert` in `mailbox.c`). A one-pass wipe of a matching M4's word now drops that pass's frames too (about 200-300 ms UNAVAILABLE on the M4: fails safe, and a wipe is a fault). After an M4-only reset into an image with another layout, the M7 still sees the old M4 word until the new image's `mailbox_init()` rewrites it, so the M4 setup calls it as early as possible (bounded, benign window: the new M4 baselines at its first read).
- **Bounded loss (user, 2026-11-03, narrows D-093 item 5):** a frame still pending when the next frame of its slot is offered is replaced and counted (`write_overruns`); the M4's E2E check (max delta 1) reports the gap as WRONG_SEQUENCE. This needs the HSEM refused for a whole message cycle (>= 20 passes for 0x020), which is a fault, not contention.
- **Reader + forward:** each M4 -> M7 slot is read under its HSEM (a refused HSEM = no frame this pass, `read_busy`). The first read only takes the baseline (a frame from before an M7 reset is never forwarded); afterwards a different `write_seq` (inequality, wrap harmless) is a new frame unless the M4 layout word differs or `len` is not the gen/ length; such a frame is dropped and its `write_seq` absorbed, so it is never forwarded later. The layout word is checked at read time: an M4 image whose word differs never gets a frame forwarded, while a frame committed during a transient wipe of a matching M4's word (rewritten every M4 pass) and read after the rewrite is forwarded; the bus receivers' E2E check still applies. A new frame goes verbatim (never re-signed) to FDCAN2 through `can_if_write()`, on its own dedicated replace-on-new TX buffer (0x023 safety range, 0x082 heartbeat; D-054 item 6, safety-reviewer MAJOR-1): `mailbox_init()` registers both IDs and must run **before** `comms_apply_filters()` (after it the port is sealed: init returns false and the module stays inert); TX_FULL retries next pass (a newer frame replaces it: `forward_overruns`), bus-off/latched drops it. The comms pass polls every 1 ms, at least four times per 0x023 cycle.
- **Health and DTCs (D-093 amendment 3 + addendum, E-28 (3)):** `mailbox_health(now)`: `layout_mismatch` when the M4 layout word differed for longer than the shortest M4 -> M7 E2E timeout (60 ms), `stale_slots` (bit = slot index) when an M4 -> M7 slot had no new frame within its gen/ E2E timeout, plus counters. Every initialised `mailbox_step()` latches its flags (`update_latches()`, sticky against the ms wrap, only in the step) and reports two level-triggered DTCs to `services/diag` (one definition, `dtc_levels()`, also behind the health fields `dtc_layout_mismatch` / `dtc_slot_frozen` / `frozen_slots`, whose stale check is evaluated at the caller's `now`): **`SAFETY_MAILBOX_LAYOUT_MISMATCH` U0300-00** fails when the M4 word matched once and a mismatch outlasted the grace, or never matched within `MAILBOX_PEER_BOOT_BUDGET_MS` (2000 ms after `mailbox_init()`; the D-101 item 3 value; `peer_missing`): before its first match the M4 is booting, not mismatched. **`SAFETY_MAILBOX_SLOT_FROZEN` U3000-87** fails when a slot is stale while the layouts match, the matched run outlasted its E2E timeout (armed), and the slot delivered a new frame since `mailbox_init()` or the boot budget is over (a warm reset keeps a matching M4 word in SRAM4 while the M4 initialises); a mismatch inside the grace holds the frozen level and does not restart the matched run; a slot that already delivered stays armed over a re-match (an M4-only reset raises it until its frames return). Never together with the mismatch DTC (one root cause = one DTC). `write_dropped` alone never sets a DTC. An inert mailbox reports nothing (E-28 (4): the image setup must check `mailbox_init()`). **Diagnostic only (user 2026-11-05):** `services/diag` keeps both out of the 0x081 DEGRADED and ERROR_COUNT, so they are no safety mechanism. Residual: the core's `fresh_at` stale check wraps after 49.7 days of a frozen slot (testFailed passes for one timeout window; confirmedDTC stays).
- **One context per slot:** `mailbox_offer()` (only from `com_send()`) and `mailbox_step()` (only from `comms_pass()`) both run in the comms task, and so do all of rt-core's platform senders (heartbeat, lean_tx, the republisher; a future 0x120 sender must too). CI greps both call sites and the `hal/hsem.h` users.
- **Open (ISSUES):** the M4's availability follows FDCAN2: while the platform port is bus-off the senders commit no counter, so no new 0x020/0x081 reach the M4 and it falls back on timeout (D-042), which is safe but couples the safety partition to the platform bus. Changing it means changing the D-056 commit rule (user decision). 0x022 and 0x120 have no rt-core sender yet: their slots stay unwritten and the M4 sees them as timed out; 0x120 must come from rt-core's own state only (D-072 item 7) and reaches its slot through the same `com_send()` hook once its sender exists.
